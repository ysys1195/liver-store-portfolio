# 要件定義

## 1. 目的

ANYCOLORのエンジニア職への応募時に提示する、非公式・非商用のECポートフォリオを制作する。

単なるEC画面の再現ではなく、人気商品の販売開始直後に発生しうるアクセス集中を題材に、フロントエンドとBFF、DB整合性、エラーUXまで含めた設計力を示す。

## 2. 想定ユーザー

- 採用担当者
- 面接官
- 開発者本人

一般公開を目的としない。

## 3. 公開・誤認防止要件

- Vercelへデプロイする
- Basic認証を必須とする
- Basic認証情報は環境変数で管理する
- 初回TOP表示時に、非公式ポートフォリオであることをモーダル表示する
- モーダルは確認操作を行うまで閉じられない
- 確認状態はセッション単位で保持する
- 全ページのフッターに非公式・デモ表記を表示する
- Demo Checkoutでも実際の注文・決済が発生しないことを明示する
- `noindex, nofollow` を設定する
- `robots.txt` でクロールを拒否する
- 実決済は実装しない
- 公式サイトと誤認させる表現を避ける
- 利用権を確認できない公式アセットを使用しない

## 4. 画面要件

### TOP

- Hero
- 注目商品
- 新着商品
- 商品一覧への導線
- ライバー紹介
- 非公式表記

### 商品一覧

- 商品カード一覧
- カテゴリフィルタ
- 販売状態表示
  - 販売中
  - 残りわずか
  - SOLD OUT
  - COMING SOON
  - 販売終了

### 商品詳細

- 商品画像
- 商品名
- 価格
- 商品説明
- 販売期間
- 在庫状態
- 数量選択
- カート追加
- Loading
- Error
- Retry

### カート

- 商品一覧
- 数量変更
- 削除
- 小計
- 空状態
- Demo Checkoutへの導線
- カート状態はZustandで管理し、ブラウザの`localStorage`へ保存する
- 保存済みデータはクライアント側のhydration完了後に表示する
- 数量は商品詳細表示時に取得した在庫数を上限とし、UIとstoreの両方で超過を防ぐ
- 商品詳細ではカート内の数量を差し引いて追加可能数を計算し、上限到達時は追加を無効化する
- カート内の価格・在庫は表示用スナップショットであり、注文時の権威ある値として扱わない
- カート表示時も商品ごとの在庫Queryで最新在庫を確認する
- 最新在庫が0の商品はカートから自動削除し、商品名と削除理由を赤文字で通知する
- 自動削除通知はsessionStorageへ保存し、同じタブでは利用者が「×」で閉じるまで再表示する
- 閉じた通知は削除し、新たな在庫切れ削除が発生した場合は再度表示する
- 在庫取得に失敗しただけではカートの商品を削除しない

### Demo Checkout

- 実決済を行わない
- カートのID・数量でデモ注文を確定し、DBの注文記録・在庫更新を行う
- 成功時は注文番号・サーバー確定金額を表示する
- pending中は確定ボタンをdisabledにし、重複送信を防ぐ
- 409時は最新在庫をrefetchして表示し、カートへ戻って数量を変更できる
- 結果不明時は同じキー・内容で手動再確認する。キーは送信前にsessionStorageへ保存する
- 成功結果は同じタブで保持し、再読み込みで注文を再作成しない
- TOPへ戻る導線を表示する

### Flash Sale Simulation

- デモ商品の在庫をリセットできる
- 複数の購入リクエストを並行送信できる
- 成功数・在庫競合数・重複リクエスト数・残在庫を表示する

## 5. EC / 技術要件

### Loading

- 商品取得時はSkeletonを表示する
- Mutation中は操作対象だけをpending表示する

### Retry

- 在庫GETは通信エラーと5xxに限って最大2回まで自動Retryする
- 商品なしを示す404は自動Retryしない
- 自動Retry後も失敗した場合は手動Retry UIを表示する
- 注文処理はIdempotency Keyを前提に安全な再送を設計する

### Error Handling

エラー内容に応じてユーザー向け文言を変える。

例:

- 商品取得失敗
- 在庫切れ
- 注文失敗
- 不正な入力
- 想定外エラー

### API Cache

TanStack Queryを使用し、必要なクライアント取得データをキャッシュする。
商品在庫は30秒でstaleとし、HTTP側には保存せずQuery側で再取得を管理する。

### stale data

- キャッシュ中の在庫とDB在庫が異なるケースを考慮する
- 購入APIでは画面上の在庫を信用しない
- 409受信後は該当商品のQueryをinvalidateして最新状態を取得する
- 必要に応じてwindow focus時のrefetchを利用する
- 商品詳細の在庫はstale状態でwindow focusした場合にrefetchする
- 再取得した在庫数と販売状態を、在庫表示、販売状態バッジ、購入CTA、数量上限へ反映する
- 最新在庫のLoading中または最終取得失敗時は、未確認の在庫を根拠にカートへ追加させない

### ボタン連打防止

Mutation中は購入・カート追加ボタンをdisabledにする。

これはUX上の防止策であり、サーバー側の二重注文防止とは分離する。

### 二重注文防止

- 注文ごとにIdempotency Keyを発行する
- 同じKeyによる再リクエストで注文を重複作成しない
- サーバー側で一意性を保証する

### 在庫競合

- DB側で条件付きUPDATEを行う
- `stock >= quantity` の場合のみ在庫を減算する
- 在庫不足時は409 Conflictを返す
- 在庫減算と注文作成は同一トランザクション内で行う

## 6. 複数ライバー対応

MVP時点から以下を考慮する。

- 1商品に複数ライバーを紐付けられる
- コラボ商品に対応可能
- 商品とライバーは多対多
- 将来的なCollection、Variant、Inventory分離を想定する

## 7. 非機能要件

- Desktop / Mobileのレスポンシブ対応
- アクセシビリティを意識したHTML
- TypeScript strict運用を基本とする
- Zodによるサーバー入力検証
- 秘密情報をクライアントへ露出しない
- エラー詳細やDB情報をクライアントへ返さない
- Unit / Component / E2Eテストを用意する

## 8. MVP対象外

- 本物の決済
- 配送
- メール送信
- 会員ログイン
- 注文履歴
- 管理画面
- Shopify連携
- 実運用向けの大規模負荷試験
- Variant / SKU単位の本格的な在庫管理

### Checkoutの通信待機・操作表示

- 注文mutationは`networkMode: always`とし、オフラインで待機した注文をオンライン復帰時に自動送信しない。通信失敗時は同じキー・内容での手動再確認を案内する。
- 注文リクエストはレスポンス本文の取得まで含めて15秒でタイムアウトし、fetchをabortする。これはサーバー側の注文取消を意味しないため、キーを保持し結果不明として扱う。
- 在庫refetchは注文mutationの完了を待たせず、独立したQueryでloading・errorを表示する。再取得失敗時は保存済みの古い在庫を「最新」と表示せず、手動再取得を表示する。
- 確定ボタンは有効時にホバーで色を変え、ポインターを表示する。無効時は薄く表示し、禁止カーソルにする。キーボード操作時にはフォーカス枠を表示する。
